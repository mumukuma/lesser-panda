# 中國個體建檔放寬 — 可行性分析與執行計劃

> 起草：2026-07-24（Claude 與維護者討論後）
> 目的：讓「有名字、有性別、綁得上園，但無官方佐證」的中國個體也能建檔上站，同時不破壞「wiki 為唯一權威、官方優先」的核心原則。
>
> ✅ **已實施（2026-08-08 註）**：階段 A–E 皆完成（政策入 `CLAUDE.md`、`has_official_source` 旗標、網站「維護者提供・未經官方佐證」標記）。
> **兩處後續政策修訂已覆蓋本文**：①檔案卡 `zoos:` 起始年**不知則留空**（2026-07-24 定案，覆蓋本文 §6「填首次確認年份、不可留空」）；
> ②性別門檻放寬——**有已建條目的家系連結者 `sex` 可留空**（2026-08-02，覆蓋本文 §3/§6「性別必填」）。現行規則一律以 `CLAUDE.md`〈資料有限個體：檔案卡〉為準。

---

## 1. 背景與問題

中國園的個體常見四類資料缺口：無生日、無出生園／來園日、園方不公告死亡、家系不公布。現行 `limited-profile` 檔案卡（2026-07-17）已針對前三項設計（`born` 可空、`last_seen` 誠實記錄動向、`unverified` 標動向不明），但**建檔門檻仍要求「至少一筆官方／一手來源」**。

維護者希望放寬為：只要（1）知道名字與性別、（2）能綁定一座已登記的動物園，即可建檔——即使**沒有任何官方來源**、資料僅來自維護者親自確認的社群流通資訊。

**已澄清的決策（2026-07-24）**：

- 「只有親屬關係、沒綁任何園」的個體**不納入**——**綁園為硬門檻**，關係僅為輔助佐證。
- 網站呈現方式與資料層分級**由本計劃提出推薦方案**（見 §4、§5）。

---

## 2. 可行性分析

### 2.1 與「資料來源原則」的張力

CLAUDE.md 的核心是「wiki 是唯一正本、官方來源優先、RPF/lineage 僅為線索」。放寬到「無官方也能建」**表面上與此衝突**，但關鍵區分在於**誰為這筆資料背書**：

- ✅ **維護者親自確認**（看過社群流通名單、讀者實拍、親自比對）＝維護者以校訂者身分背書，這本身就是 wiki 權威的一環。
- ❌ **RPF/lineage 機械帶入、未經人確認** ＝ 仍只是線索，不可據以建檔。

因此放寬的**真正邊界**不是「有無官方來源」，而是「**有無維護者/人為確認**」。只要守住「不得由 RPF/lineage 腦補建檔」，就與資料來源原則相容。事實上 `xiao-xiao-bai-nanjing`（南京小小白）**已經**以「維護者提供、暫無官方公告佐證」建檔上站——本計劃是把既成實務**正式寫進政策並補上標示機制**，而非開新口子。

### 2.2 現有機制盤點（多數已就緒）

| 需求 | 現有機制 | 狀態 |
|------|----------|------|
| 缺生日/rpf_id 不報警 | `audit.py` 對 `limited-profile` 降為 ⚪ info | ✅ 就緒 |
| 動向不明誠實記錄 | `last_seen` 欄（limited-profile 必填） | ✅ 就緒 |
| 動向不明排除現存統計＋顯示待查證 | `unverified` tag → `export_json` 輸出旗標 → 網站 badge | ✅ 就緒 |
| 非官方補充資料另存 | `extra_sources` 欄（與官方 `sources` 分開） | ✅ 就緒 |
| 官方／非官方來源自動辨識 | `build_db.py` 的 `is_official_source()` / `official_sources()`；個體頁只顯示官方來源 | ✅ 就緒 |
| 不夠格建檔的線索池 | `data/cn-candidates.json` | ✅ 就緒 |

**結論：可行，且工程量小。** 唯一真正缺的是「在資料層與網站層明確標示這筆個體**完全沒有官方佐證**」的旗標——而這可**從既有的官方來源分類器自動推導，不需新增任何手動 tag**（見 §4）。

## 3. 建檔門檻（新版）

一隻中國個體要建檔上站，**須同時符合**：

1. **知道名字與性別**（性別不確定則暫緩，留 `cn-candidates.json`）。
2. **綁定至少一座已登記於 `data/zoos.json` 的動物園**（硬門檻；沒綁園一律不建）。
3. 資料來源**至少一項**：官方來源／讀者實拍展牌（`extra_sources`）／**或維護者親自確認的社群流通資訊**（記為 `維護者提供（日期）`）。

**不再要求**必須有官方來源。但仍嚴禁「僅憑 RPF/lineage 機械資料、無人確認」就建檔——那類仍留 `cn-candidates.json`。

**與 §2 澄清一致**：親屬關係**不能替代**綁園。若只知「牠是某隻的孩子」卻不知在哪個園 → 不建檔，寫進對方條目的 `## 家族` 敘述 + 記 `cn-candidates.json` 即可。

不符門檻者一律進 `data/cn-candidates.json`，累積到符合再轉正（流程照現行）。

## 4. 資料層信任分級 — 推薦方案

**推薦：不新增手動 tag，改由既有官方來源分類器「自動推導」。**

理由：`build_db.py` 已有 `official_sources()`，且 DB 存的 `sources` 欄本就**只留官方來源**。因此「這隻有無官方佐證」＝「`official_sources()` 是否為空」，可完全自動判定，**無漂移風險、無需人工維護 tag**。手動 tag（如 `author-sourced`）會多一個要記得掛/拿掉的欄位，容易忘、容易錯。

**做法**：`pipeline/scripts/export_json.py` 新增一個布林旗標：

```python
"has_official_source": bool(json.loads(r["sources"] or "[]")),
```

（`r["sources"]` 在 build_db 已是過濾後的官方來源清單，空即代表無官方佐證。）

**與 `unverified` 的分工（重要，兩軸不可混用）**：

- `has_official_source`（**佐證軸**）：這筆紀錄有沒有官方背書。**推導**、不手動。
- `unverified`（**在世軸**）：這隻動向明不明（最後確認距今約 2 年以上）。**維持現行語意**，手動掛。

一隻「維護者確認、現正在世」的新個體 = `has_official_source: false` + **不掛** `unverified`。切勿為了觸發標示而濫掛 `unverified`，否則會把「在世但無官方佐證」誤標成「動向不明」，污染在世統計。

> 備選方案（不推薦）：新增 `author-sourced` 手動 tag。僅在維護者日後想「即使有官方來源、仍想手動標維護者存疑」等細分需求時才值得，屆時再加。

## 5. 網站呈現 — 推薦方案

**推薦：上站 + 顯示「未經官方佐證」標記（重用現有待查證 badge 樣式），計入總數；在世統計照在世軸處理。**

| 面向 | 推薦處理 |
|------|----------|
| 是否上站 | **上站**。牠們是真實個體，藏起來違背「讓訪客看到中國個體」的初衷。 |
| 視覺標記 | 個體頁與卡片顯示一枚 **「維護者提供・未經官方佐證」** 標記（沿用 `unverified` 待查證 badge 的樣式，但文案不同，避免與「動向不明」混淆）。**觸發條件：`limited_profile === true && has_official_source === false`**（⚠️ 不可只用 `has_official_source===false`——全庫 572/673 條目本就無官方來源〔多為 RPF〕，只有檔案卡才該標；`limited_profile` 旗標已於階段 B 一併輸出）。 |
| 個體頁來源區塊 | 現行邏輯已「只顯示官方來源」→ 這類個體來源區塊**自然為空**，正好配合標記說明「本條目暫無官方來源」。 |
| 條目總數 | **計入**（真實個體）。 |
| 在世統計 | 依**在世軸**：`died` 空且未掛 `unverified` → 算現存。佐證軸不影響在世統計。 |

> 保守選項（維護者可選）：若不希望無官方佐證者灌水「現存」數字，也可讓網站在現存統計中排除 `has_official_source === false`。但這會把兩軸綁在一起、語意較糊；**預設不採用**，除非維護者明確要求。

「暫不上站只存 wiki」的選項**不推薦**——那等於現行 `cn-candidates.json` 的角色，沒必要為它建 md 條目。

## 6. slug 與 frontmatter 規則（沿用現行、無需新規）

因綁園為硬門檻，slug 完全沿用檔案卡現行規則：

- **有生日**（含只知年份）→ `名字-生日`。
- **完全無生日** → `slugify(名字)-園簡稱`（園簡稱用首次確認所在園的英文/城市名，如 `xiao-bai-shanghai`）；同園撞名再加序號。查到生日後照 rename 流程改回 `名字-生日`。

frontmatter 重點：

- `sex:` 必填（門檻）。
- `born:` 有據才填，無則留空。
- `last_seen:` 必填（最後確認在世/在園日期）。
- `zoos:` 只登有佐證出現過的園，起始年填「首次確認年份」（不可留空，否則被誤標 🐣 出生地）。
- `tags:` 含 `limited-profile`；動向不明才加 `unverified`。**不需**新增佐證相關 tag。
- `sources:` 有官方就填官方；**純維護者確認則寫 `維護者提供（YYYY-MM-DD）`**。讀者實拍展牌放 `extra_sources`。
- 家系/出身若為維護者提供而未經官方 → 內文相應處標 `🚧 待查證`。

## 8. 風險與守則

- **最大風險：無官方佐證條目被誤讀為既定事實。** → 由 `has_official_source` 自動標示 + 個體頁來源區塊留空 + 內文 `🚧 待查證` 三重提示化解。
- **守住紅線**：維護者親自確認才可建；RPF/lineage 機械資料不可建，續留 `cn-candidates.json`。
- **兩軸不混用**：佐證軸（自動）≠ 在世軸（`unverified`，手動）。禁止為觸發標示而濫掛 `unverified`。
- **官方後補即自動升級**：日後補進官方來源，`has_official_source` 自動轉 true、標記自動消失，無需手動改 tag——這正是「推導而非手動」的最大好處。
- **綁園仍是硬門檻**：沒綁園、只有名字或關係 → `cn-candidates.json`，不建 md。
